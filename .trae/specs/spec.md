# Телеграм-бот реферальной программы и розыгрышей - Product Requirements Document

## Overview
- **Summary**: Асинхронный Telegram-бот на Python (aiogram 3.31) для управления платным каналом: реферальная система с звёздами, маркет рефералов, уровни участников, розыгрыши между подписчиками, финансовый модуль (пополнение/вывод звёзд).
- **Purpose**: Монетизация платного канала через реферальную программу, создание системы поощрений за продление подписки и удержание участников через уровневую систему и розыгрыши.
- **Target Users**:
  - Участники платного канала: покупают реф-ссылки, приглашают друзей, участвуют в розыгрышах, торгуют рефералами на маркете.
  - Администратор/владелец канала: создаёт розыгрыши, управляет уровнями, обрабатывает заявки на вывод.

## Goals
- Реализовать реферальную систему с вознаграждением за приглашение и продление подписки.
- Создать уровневую систему, мотивирующую долгосрочное пребывание в канале.
- Реализовать маркет для покупки/продажи рефералов между участниками.
- Создать систему розыгрышей без необходимости взаимодействия участников.
- Реализовать финансовый модуль: баланс звёзд, пополнение, заявки на вывод.

## Non-Goals
- Интеграция с реальными платёжными шлюзами (заменяется на ручное подтверждение админом или Telegram Stars как заглушка).
- Веб-интерфейс управления (всё через Telegram-меню админа).
- Множество каналов — бот работает с одним целевым платным каналом.
- Многоуровневая реферальная программа (только прямой пригласивший → реферал).

## Background & Context
- Стек: Python 3.11+, aiogram 3.31, aiosqlite (асинхронный SQLite с WAL-mode), python-dotenv.
- Все библиотеки должны быть асинхронными.
- Внутренняя валюта: «звёзды» (зв.).

## Functional Requirements

### Реферальная система
- **FR-1**: Участник может создать персональную реферальную ссылку на платный канал стоимостью 111 звёзд (списываются с баланса).
- **FR-2**: За каждого приглашённого участника, купившего/активировавшего доступ по ссылке, пригласивший получает 40 звёзд.
- **FR-3**: За каждое продление подписки приглашённым рефералом его пригласивший получает 20 звёзд.
- **FR-4**: Участник видит список своих рефералов (имя/ID, уровень).

### Топ рефоводов
- **FR-5**: Доступна команда «Топ рефоводов», показывающая рейтинг по количеству активных рефералов (от большего к меньшему).

### Маркет рефералов
- **FR-6**: Участник может выставить N своих рефералов на продажу по указанной цене за штуку (лот).
- **FR-7**: Участник может просмотреть список лотов на маркете: продавец, количество рефералов, цена за 1 шт., уровень рефералов, ID/имя.
- **FR-8**: Участник может купить лот с маркета: списываются звёзды с баланса покупателя, начисляются продавцу, рефералы переходят к покупателю.
- **FR-9**: Продавец может отменить свой активный лот.

### Уровневая система
- **FR-10**: Каждому участнику присваивается уровень. Уровень = количество полных месяцев непрерывной активной подписки (L1 = 1 месяц, L2 = 2 и т.д.).
- **FR-11**: При не продлении подписки вовремя уровень участника сбрасывается на 0.
- **FR-12**: Участник может восстановить предыдущий уровень (максимальный когда-то достигнутый) за разовую оплату 100 звёзд.
- **FR-13**: Администратор может вручную назначить любому участнику любой уровень.
- **FR-14**: Уровень участника влияет на вес (шанс) в розыгрышах пропорционально: чем выше уровень, тем больше шанс.

### Розыгрыши
- **FR-15**: Администратор может создать розыгрыш: текст объявления, приз, дата/время завершения, условие (активная подписка на платный канал), опционально — фильтр по минимальному/максимальному уровню.
- **FR-16**: Созданный розыгрыш автоматически публикуется ботом в указанный Telegram-канал.
- **FR-17**: В розыгрыше автоматически участвуют все соответствующие условиям участники; кнопок/действий для участия не требуется.
- **FR-18**: В момент завершения бот случайным образом выбирает победителя с учётом веса уровней, публикует результат в канал и уведомляет победителя в ЛС.

### Финансовый модуль
- **FR-19**: У каждого участника есть баланс в звёздах.
- **FR-20**: Участник может создать заявку на пополнение баланса (админ получает уведомление и подтверждает вручную, начисляя звёзды).
- **FR-21**: Участник может создать заявку на вывод звёзд (указать реквизиты); бот отправляет заявку владельцу/админу для обработки вручную.
- **FR-22**: Администратор видит список всех заявок на пополнение/вывод и может подтвердить или отклонить.

### Команды и меню
- **FR-23**: Главное меню пользователя: Профиль, Баланс, Мои рефералы, Реф. ссылка, Топ рефоводов, Маркет рефералов, Розыгрыши, Пополнить, Вывести, Админ-меню (для админа).

## Non-Functional Requirements
- **NFR-1**: Бот работает асинхронно; все I/O операции (БД, запросы к Telegram API) — через async/await.
- **NFR-2**: SQLite работает в режиме WAL для повышенной производительности при параллельных записях.
- **NFR-3**: Все секретные данные (токен бота, ID канала, ID админа) хранятся в `.env` через `python-dotenv`.
- **NFR-4**: Код разбит на модули (handlers, keyboards, database, states, utils, config).
- **NFR-5**: Обработка ошибок: исключения ловятся и логируются, пользователю показывается дружелюбное сообщение.
- **NFR-6**: Планировщик задач (APScheduler или aiogram JobQueue) для завершения розыгрышей и проверки истечения подписок.

## Constraints
- **Technical**: Python 3.11+, aiogram==3.31, aiosqlite, python-dotenv, APScheduler (asyncio compatible).
- **Business**: Стоимость реф-ссылки 111 звёзд, награда за реферала 40 звёзд, за продление 20 звёзд, восстановление уровня 100 звёзд.
- **Dependencies**: Telegram Bot API (бот должен быть админом канала с разрешением на отправку сообщений и инвайт-ссылки).

## Assumptions
- Подписка и продление условные — активируются через начисление админом или покупкой реф-ссылки. При необходимости можно интегрировать Telegram Stars.
- Реферал «переходит» к новому владельцу в рамках учёта бонусов за последующие продления (FR-3).
- Максимальный достигнутый уровень хранится отдельно от текущего, чтобы реализовать восстановление (FR-12).

## Acceptance Criteria

### AC-1: Создание реферальной ссылки
- **Type**: `rule`
- **Given**: Пользователь имеет баланс ≥ 111 звёзд и ещё не имеет активной персональной ссылки.
- **When**: Нажимает «Создать реф-ссылку».
- **Then**: С баланса списывается 111 звёзд, генерируется уникальная пригласительная ссылка на канал, пользователь получает ссылку.
- **Pass Condition**: В БД создана запись о ссылке, баланс уменьшен ровно на 111, пользователю отправлена ссылка.
- **Evidence**: Проверить запись `referral_links` в БД и транзакцию баланса; лог сообщения пользователю.

### AC-2: Награда за приглашённого реферала
- **Type**: `rule`
- **Given**: Пользователь A перешёл по реф-ссылке пользователя B и приобрёл/активировал подписку.
- **When**: Регистрируется факт активации подписки A.
- **Then**: Баланс B увеличивается на 40 звёзд, в БД отмечено, что A — реферал B.
- **Pass Condition**: `balance` B увеличен на 40; в `referrals` есть запись referrer=B, referee=A.
- **Evidence**: Транзакция в БД и уведомление B о начислении.

### AC-3: Награда за продление рефералом
- **Type**: `rule`
- **Given**: A — реферал B, у A продлена подписка.
- **When**: Обработчик продления выполняется.
- **Then**: Баланс текущего владельца реферала A (может быть не B, если реферал был продан) увеличивается на 20 звёзд.
- **Pass Condition**: Начисление 20 звёзд на счёт владельца реферала.
- **Evidence**: Запись в истории транзакций.

### AC-4: Топ рефоводов сортируется по убыванию
- **Type**: `rule`
- **Given**: В БД N пользователей с разным количеством рефералов.
- **When**: Запрос «Топ рефоводов».
- **Then**: Ответ показывает список от большего к меньшему, с количеством рефералов.
- **Pass Condition**: Порядок соответствует подсчёту по `referrals`.
- **Evidence**: Сравнить ответ бота с SQL-запросом `ORDER BY count DESC`.

### AC-5: Выставление реферала на маркет
- **Type**: `rule`
- **Given**: У пользователя X есть ≥1 реферал, который не выставлен на продажу.
- **When**: X создаёт лот: 2 реферала по 50 звёзд за штуку.
- **Then**: Создаётся активный лот в БД, эти 2 реферала временно «забронированы» за лотом.
- **Pass Condition**: Лот существует, статус `active`, рефералы не могут быть повторно выставлены до отмены/продажи.
- **Evidence**: Запись в `market_lots` и флаг у рефералов.

### AC-6: Покупка лота на маркете
- **Type**: `rule`
- **Given**: Лот L существует (2 реферала по 50 = 100), у покупателя Y баланс ≥ 100 звёзд.
- **When**: Y нажимает «Купить» на лоте L.
- **Then**: С Y списывается 100, продавцу Z начисляется 100, оба реферала переходят в собственность Y, лот закрыт.
- **Pass Condition**: `referrals.owner` обновлён на Y; балансы изменены; статус лота `sold`.
- **Evidence**: Транзакции в БД и уведомления обеим сторонам.

### AC-7: Уровень растёт с месяцами подписки
- **Type**: `rule`
- **Given**: Участник имеет активную подписку 2 полных месяца (61+ дней).
- **When**: Планировщик раз в день пересчитывает уровни.
- **Then**: Уровень участника = 2.
- **Pass Condition**: `users.level == 2`.
- **Evidence**: После моковой даты начала 65 дней назад уровень повышается.

### AC-8: Сброс уровня при просроченной подписке
- **Type**: `rule`
- **Given**: Участник имел уровень 3, подписка истекла 3 дня назад и не продлена.
- **When**: Планировщик проверяет истечение.
- **Then**: Текущий уровень становится 0, но в `users.max_level` остаётся 3.
- **Pass Condition**: `level == 0` AND `max_level == 3`.
- **Evidence**: Проверка полей БД после запуска проверки.

### AC-9: Восстановление уровня за 100 звёзд
- **Type**: `rule`
- **Given**: Участник уровень=0, max_level=5, баланс≥100.
- **When**: Нажимает «Восстановить уровень».
- **Then**: -100 звёзд, уровень=5 (max_level).
- **Pass Condition**: Баланс-100, level=max_level.
- **Evidence**: Транзакция и поле `level`.

### AC-10: Админ назначает уровень
- **Type**: `rule`
- **Given**: Пользователь админ U, участник V.
- **When**: U отправляет команду «/setlevel V 4».
- **Then**: У V текущий уровень становится 4, max_level также обновляется при необходимости.
- **Pass Condition**: `level=4`.
- **Evidence**: Проверка БД.

### AC-11: Создание розыгрыша админом
- **Type**: `rule`
- **Given**: Админ проходит пошаговый FSM: текст, приз, время, канал, опционально уровни 3+.
- **When**: FSM завершён.
- **Then**: Создаётся запись `giveaways`, в целевой канал отправлено сообщение-объявление о розыгрыше.
- **Pass Condition**: Запись в БД и `message_id` в канале.
- **Evidence**: Сообщение в тестовом канале и запись БД.

### AC-12: Завершение розыгрыша с весом уровней
- **Type**: `rule`
- **Given**: Розыгрыш G с условием подписка, фильтр L>=2. Участники: A(L2), B(L3), C(L1) — C не проходит по фильтру.
- **When**: Время завершения наступило.
- **Then**: Победитель выбирается между A и B; вес A=2, B=3. Результат публикуется в канал, победитель уведомлён.
- **Pass Condition**: Победитель — только A или B; сообщение в канале содержит победителя.
- **Evidence**: 1000 запусков — A:B ≈ 2:3 статистически, C никогда не побеждает.

### AC-13: Заявка на вывод уходит владельцу
- **Type**: `rule`
- **Given**: Пользователь баланс ≥ 50 звёзд.
- **When**: Создаёт заявку «вывести 50, кошелёк X».
- **Then**: Заявка на вывод создана в БД, админ/владелец получает уведомление с деталями.
- **Pass Condition**: Запись в `withdraw_requests` и сообщение админу.
- **Evidence**: Проверка БД и полученного админом сообщения.

### AC-14: БД использует WAL режим
- **Type**: `rule`
- **Given**: Бот запущен.
- **When**: Выполнено `PRAGMA journal_mode`.
- **Then**: Возвращается `wal`.
- **Pass Condition**: journal_mode == wal.
- **Evidence**: Лог подключения к БД.

### AC-15: Качество структуры проекта
- **Type**: `rubric`
- **Dimension**: Модульность и читаемость структуры кода.
- **Scale**: 1-5
- **Anchors**: 1 = весь код в одном файле; 3 = 3-4 логичных модуля; 5 = чёткое разделение: config, loader, db repo, handlers (user/admin), keyboards, states, utils/scheduler.
- **Pass Threshold**: >= 4
- **Evidence**: Обзор дерева проекта.

### AC-16: Качество обработки ошибок и валидации
- **Type**: `rubric`
- **Dimension**: Обработка граничных случаев (недостаточно средств, несуществующий пользователь, не админ пытается вызвать админ-команду).
- **Scale**: 1-5
- **Anchors**: 1 = необработанные исключения, краши; 3 = основные случаи; 5 = все случаи FR покрыты проверками, понятные ответы пользователю.
- **Pass Threshold**: >= 4
- **Evidence**: Ручные сценарии: покупка при нуле; неадмин вызывает /giveaway; отменить чужой лот.
